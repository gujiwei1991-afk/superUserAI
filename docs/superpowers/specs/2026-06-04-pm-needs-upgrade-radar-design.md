# 设计：给 PMAgent 加「治标 → 治本升级雷达」

- 日期：2026-06-04
- 状态：已通过设计评审，待写实现计划
- 落点：`backend/app/agents/prompts/pm_prompts.py` 的 `SYSTEM_PROMPT`（纯 prompt 改动）

## 1. 背景与问题

提需求的同事**通常不是程序员**，提的往往是「表层解决方案」而非「根因需求」。典型例子：一个下拉框现有选项 1 2 3 4，需要再加 5 6——用户会直接说"加 5 6"，而专业判断应识别出"选项会持续变动，应把数据源做成可配置"。这类「治标不治本」的需求很多，不止可配置一类。

### 现状诊断

1. **澄清对话阶段已具备升级意识。** 新需求走 `NEW_PROJECT`/`CHAT` 意图 → `PMAgent.chat` → `SYSTEM_PROMPT`。现有 prompt 的原则 3（挖"真正想解决的麻烦"、不照单全收）和原则 5（列 2-3 个方案让用户挑）已经覆盖了这个方向，例子里甚至有"导出 Excel → 其实要仪表盘""配置项手动改 vs 自动联动"。
2. **效果取决于模型遵循度。** `.env` 默认 `LLM_MODEL=gpt-4.1-mini`，prompt 写了 ≠ 每次都做到。当前原则 3/5 偏「思维原则」，缺少可对照的**具体模式清单**，模型容易泛泛而谈、不主动升级。
3. **`MODIFY` 路径不带升级引导，但不是主战场。** 项目进入 `reviewing` 后，"再加个 5 6"（命中"再/改"等词）被分类为 `MODIFY` → `modify_prd` 直接重写 PRD、通知审核，不经升级引导。**但**：升级的最佳时机是"方案成型之前"的澄清阶段；等到 reviewing 之后的微调再反问"要不要可配置"已经晚了、还打断节奏。故本期不动 MODIFY。

### 结论

把战场集中在**澄清对话阶段**，将原则 3/5 从「思维原则」强化为「带具体模式清单 + 强克制规则的升级雷达」。这是最小改动拿下绝大多数价值。

## 2. 目标

- PMAgent 在第一次听到「表层方案型」需求时，能对照内置模式**主动、温和地提议**更治本的方案，给推荐 + 理由，**由用户最终拍板**。
- 覆盖一组常见模式（不止可配置），开放可扩展。
- **强克制**：不啰嗦、不镀金、简单需求不硬塞、被拒即停。

### 非目标（不做项）

- 不加独立的「需求反模式分类器」（YAGNI，prompt 内联判断已足够）。
- 不改意图路由、不动 `modify_prd`/`MODIFY` 路径。
- 不改任何代码逻辑——纯 `SYSTEM_PROMPT` 改动。

## 3. 设计

### 3.1 改动位置

仅 `SYSTEM_PROMPT`，在现有原则 3（挖根因）与原则 5（列方案让用户选）之间，植入一个「升级模式参照表 + 克制规则」小节，作为这两条原则的"具体化弹药"。其余原则、`PRD_GENERATION_PROMPT`、`modify_prd` 调用文案均不变。

### 3.2 升级雷达清单（内置参照，非穷举）

| 表层说法（治标信号） | 背后根因 | 升级方向 | 提议话术骨架 |
|---|---|---|---|
| "加个选项 5 6 / 再加一项"——写死的枚举 | 选项会持续变 | 数据源可配置 | "这些选项以后还会加吗？要不做成你后台能自己加减的，省得每次找人改" |
| "导出 Excel 我自己看 / 每周导一次" | 其实要看某个结果 | 仪表盘·自动汇总 | "你导出来主要看哪个数？要不做个页面自动算给你看" |
| "这条帮我改成 X / 把这几个都改了"——一条条手动 | 量大、重复 | 批量操作 | "这种要改很多条吗？要不能一次选多条一起改" |
| "A 改了我再手动改 B" | 两处该联动 | 自动联动 | "A 变的时候 B 自动跟着变好不好？省得两头改" |
| "列表太长找不到 / 一直翻页" | 检索难 | 搜索·筛选 | "加个搜索框或按条件筛，直接定位？" |
| "给他也开个权限"——逐人开 | 角色化 | 权限分级 | "按岗位分下谁能看谁能改？比一个个开省事" |

prompt 中需明确：这些是**参照而非穷举**，遇到同类"治标"信号就照此思路办。

### 3.3 克制规则（与清单同等重要）

- **信号明确才提**；整轮对话**最多提一次**这类升级，不反复念叨。
- 提议 = **一句话方向 + 一句"帮你省什么事"**，不长篇、不堆技术词。
- 用户说"就按我说的做" → **立刻回到原方案，不再劝**。
- **双向判断**：升级方案若明显更贵、而用户的简单诉求确实够用（一次性、不会变），**不但不升级，反而帮他砍掉镀金**——呼应原则 4「代价远高于价值时要劝阻」。升级是为解决真问题，不是为做大而做大。
- 真·简单需求**不硬塞**升级（强化原则 5 的"简单需求别硬塞 2 个选项"）。

## 4. 验证（真机对话）

部署后在企微群（记得 @机器人）实测：

| 输入 | 期望表现 |
|---|---|
| "我要个下拉框选 1234" | 温和提议"选项以后会变吗？要不可配置" |
| "帮我把这条记录改成 X"（单条、一次性） | **正常照做、不硬升级**（克制规则生效） |
| "导出 Excel" | 反问"主要看哪个数"，提议仪表盘 |
| "给小王也开个权限" | 提议按岗位分权限 |

判据：该提的提了且只提一次；不该提的（简单一次性需求）不打扰。

## 5. 风险

- **过度升级**：内置清单可能诱导模型"什么都建议做大"。由克制规则的"双向判断 + 简单需求不硬塞 + 最多提一次"对冲；验证用例专门包含"单条修改不应升级"的反例。
- **模型遵循度**：`gpt-4.1-mini` 对长 prompt 的执行力有限。清单用「信号→话术」的具体配对（而非抽象原则）来提升可执行性；若实测仍不理想，再考虑升级模型或方案二/三。
